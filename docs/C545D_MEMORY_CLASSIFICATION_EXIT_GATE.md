# C545D — 残存メモリ増加の分類・検証完了条件（2026-11-23）

**開発PR #62専用の分類契約。実機への適用許可ではない。** 状態の機械可読な原本は [MEMORY_CLASSIFICATION_CASES.json](MEMORY_CLASSIFICATION_CASES.json)。`tests/validate_c545d_memory_classification_cases.py` とCIで検査する。

## 方針を変更した理由

旧手順は「増加を観測 → 疑わしい箇所を修正 → 16/256サイクルの相対変化を調べる」の繰り返しで、何をもって終了とするか、どの観測ならリークと確定するか、失敗時に何の証拠が欠けたかを先に定めていなかった。実際、[Windows #45033642809](https://github.com/taku077/c545d-recorder/actions/runs/45033642809) の一時パス再利用案はPrivateUsageが1ページ（4096 B）減っただけでREGIONコミットは69632 B増えた。これをメモリリーク修正として採用しない。成功した修正でもOSへ返されたPrivateUsageが0とは限らない。指標を取り違えない。

Microsoft公式の[PrivateUsage](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)、[PROCESS_HEAP_ENTRY](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-process_heap_entry)、[ETWヒープ割当/解放イベント](https://learn.microsoft.com/en-us/windows/win32/memory/memory-management-tracing-events)、[Outstanding allocationsの意味](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/using-actions-to-analyze-process-heap-data)を測定の定義とする。

## 厳密に区別する四つの分類

1. **確認済みの解放漏れ（LEAK_CONFIRMED）** — 同じPID、同じ割当器、同じ比較窓で、割当IDと解放IDを照合して持越し残存が増加し、発生する関数と所有者が分かる。正常なライフタイムの保留と非同期未完了を除外する。ソース上の参照漏れを発見しただけでは「実測の残存増加を全て説明した」とはしない。
2. **有界なメモリ保持（BOUNDED_RETENTION）** — 対象の使用中オブジェクト増が停止し、再利用可能なヒープの容量が再負荷でも際限なく増加しないという時系列証拠がある。単一の終点・小さい差・別環境の384サイクル結果だけでは足りない。
3. **処理に伴う一時的確保（TRANSIENT_LIFETIME）** — 例えばMP4のサンプル表・EOS処理について、開始から分割後まで同一PID・同じフェーズの対応で確保・解放・再利用が説明できる。プロセスの全PrivateUsage減少を必須とはしない。
4. **分類未完了（EVIDENCE_GAP）** — 「未解明」で閉じる状態ではない。**分類失敗の理由、欠けている観測、既存資料で取得できない理由、具体的な自動取得方法、判定規則**を全て付けて、未解決のリリースブロッカーとして残す。記載だけで完了扱いにしない。

分類の単位は **リソース×同一条件の負荷×ライフタイム窓**。実録画のUMDH `gstisomp4/gstbase`、カメラなしGIO/WinRTのHeapWalk、別プロセスの384サイクルVirtualQueryは別単位であり、差額を合算して一つのリークと呼ばない。

## 分類を進める判定手順

- **Step A — 再利用**：既存のWindowsアーティファクトと各ソース検証済みの生存/コミット/イベント数値を特定。冒頭で「既存のどの列に答えがないか」を示す。
- **Step B — 観測の設計**：疑問を「どの所有者の割当が、最後の同期/解放境界をまたいで残ったか」という一つの反証可能な問いに限定。必要な alloc/free ID・スタック分類・PrivateUsage・同期完了を**一度の短い隔離CI**で照合できるようにする。完全履歴でなければ `coverage=partial` とし、無かったことにしない。
- **Step C — 判定**：一致しない割当が確認されたら所有元のソースを調査してA/B修正。全対応かつコミットが残るなら有界な保持かを別の同条件の負荷窓で検証。どちらも満たせなければ「欠けた観測」と判定不能理由を具体的に更新して次の**異なる**信号を取得。
- **Step D — 時間と無駄の管理**：正確な原因/所有者を確認しない微小最適化を次々実装しない。測定失敗は失敗種類（仕様/計測/自動化/資源挙動）を記録し、同一手順をそのまま再要求しない。CI成功と実機安定を区別する。

## 合格ゲートを二層に分離

**原因分類ゲート**：ユーザーが問題としている持続的な増加について、全ケースが上の3分類のいずれかとして根拠つきで判断されること。EVIDENCE_GAPが残る間は「原因分類完了」とは宣言しない。分類が難しい場合でも、このJSONの不足信号/自動取得方法を更新し、新しい判別力のある調査を先行させる。

**運用リリースゲート**：前ゲートと独立に、製品用途としてメモリ/ハンドル/CPUの**同位相・同一PID**の増加傾向、再接続・MP4分割前後の解放と安定性、録画品質・音声・同期・EOSを検証する。CIではカメラなし疑似RTSP/実ソースミラーによるCodec・ABI・MP4/EOS回帰に合格すること。その後の**一度に統合した**実録画検証で、初期化完了後に段階的な上限・傾き・増加の反復が確認できず、録画ファイルに欠落/破損がなく、CPU・メモリ・ハンドルがリソース予算内に収まること。数値上限はユーザーPCの既存データと実機構成、利用可能メモリ/ハンドル余裕から**検証前に固定**する（仮のMB/時閾値を今発明してPASSにしない）。本当の無期限/絶対ゼロの証明はできないが、未分類の無制限増加を「問題なし」で通さない。

過去の成功条件（GStreamer 1.28.8 MSVC DLL 2047 export parity、2系統RTSP、左stream1/右stream6、2560×720 15fps、x264 medium QP24、AAC mono48kHz/192kbps、毎時MP4、avdec_h264、音声映像同期・安全EOS）はすべて必須。不明な候補を生録画PCへ導入しない。周期的な強制再起動、録画中DLL交換、レジストリ変更、任意ハンドル強制クローズは一切しない。
