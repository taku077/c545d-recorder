# C545D — Actual Windows ETW heap address lifetime adapter (2026-11-23 JST)

## Exact tested scope

Development PR [#62](https://github.com/taku077/c545d-recorder/pull/62), **disposable GitHub Actions Windows 2022 only**. This work changes the diagnostic test harness, not any installed recorder executable, GStreamer DLL, Windows 10 registry, Tapo RTSP credentials, video, audio or production settings. NuGet [Microsoft.Diagnostics.Tracing.TraceEvent 3.2.8](https://www.nuget.org/packages/Microsoft.Diagnostics.Tracing.TraceEvent/3.2.8) is pinned in `tests/C545DEtwHeapIdentity/C545DEtwHeapIdentity.csproj`. The implementation uses the public Microsoft PerfView [HeapTraceProviderTraceEventParser](https://github.com/microsoft/perfview/blob/main/src/TraceEvent/Parsers/KernelTraceEventParser.cs), with `HeapTraceAlloc`, `HeapTraceReAlloc` and `HeapTraceFree` typed payloads, filtering by the disposable fixture's owned PID.

Microsoft [ETW_HEAP_EVENT_ALLOC](https://learn.microsoft.com/en-us/windows/win32/memory/etw-heap-event-alloc), [REALLOC](https://learn.microsoft.com/en-us/windows/win32/memory/etw-heap-event-realloc) and [FREE](https://learn.microsoft.com/en-us/windows/win32/memory/etw-heap-event-free) define HeapHandle, Address, OldAddress/NewAddress and old/new size. Microsoft [Enabling Heap Data Capture](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/enabling-heap-data-capture) explains the importance of pre-workload capture. Windows 10 supports these ETW events, but **no Windows10 real Tapo test has been conducted**.

### Proven earlier coverage failure — exact diagnosis

Previous Xperf source-stack reports contained 31 groups `Alloc=0,Realloc total=3604,Out total=466`; this is a **reallocation-compatible aggregation pattern**, not proven retained 466 distinct objects. The original source-only lifetime state machine had no actual event payload adapter.

New exact native test program `tests/c545d_etw_realloc_transfer_ci.c` allocates 64 controlled 360-B blocks, reallocates 16 to 720-B through a different non-inlined function, explicitly frees 48 and holds 16 until signalled. The small ETL is captured **after process ready but before the controlled workload starts**, with sequential PID-specific Xperf, stackwalk, and zero logger lost event/buffer counters. Raw ETL, addresses, PDBs and stack names remain private to the temporary Windows runner and are deleted; only strict numeric lines appear in CI logs. Source JSON/probe logs, registry paths and media are not uploaded.

An initial C# adapter compile attempt [#45146874591 FAILURE](https://github.com/taku077/c545d-recorder/actions/runs/45146874591) lacked the `Microsoft.Diagnostics.Tracing.Parsers.Kernel` namespace. Fixed in commit [`41af535`](https://github.com/taku077/c545d-recorder/commit/41af53599281b0a2dc2e91baba390a041f8c9763).

The next real decoder [#45147076958 FAILURE](https://github.com/taku077/c545d-recorder/actions/runs/45147076958) rejected `selected_held_blocks_freed_before_trace_stop`, even though Xperf still showed 16 reallocated outstanding. The new numeric-only fail-closed diagnostic [#45147399229 FAILURE](https://github.com/taku077/c545d-recorder/actions/runs/45147399229) confirmed **64 selected 360-B allocation events, 64 observed Free events, 0 linked ReAlloc, 16 unrelated ReAlloc**, directly identifying that the relevant ETW `HeapFree` events appeared *before* the matching `HeapReAlloc` event in the typed event stream. The former direct live-map algorithm incorrectly erased the old address too soon. This was an **adapter accounting defect**, not a proof of an extra heap leak.

Commit [`7a789c6`](https://github.com/taku077/c545d-recorder/commit/7a789c6e618f20e270052f646a6b8eadb2dafae2) fixed it with a bounded **provisional-Free state**: do not permanently finalize a Free until a matching old address/heap/old size appears in the immediately subsequent ReAlloc; transfer original identity to the new address, rejecting stale (>32 intervening selected-PID heap events), duplicate Free, address collision, unknown size and orphan ReAlloc. No raw pointer ever leaves the local process. Invalid fixture tests included 13 negative mutations and 4 known valid states. Not an excuse to silently ignore arbitrary unknown events on a real-GIO run.

### Verified real ETW results

1. **[Windows #45147821386 — SUCCESS](https://github.com/taku077/c545d-recorder/actions/runs/45147821386), job 137601371931**, precleanup early stop: `C545D_ETW_REALLOC_IDENTITY_MATCHED,original_alloc=64,realloc=16,tracked_free=48,held_at_trace_stop=16,held_bytes=11520,realloc_moved=16,realloc_inplace=0,raw_selected_free=64,realloc_after_provisional_free=16,max_provisional_free_to_realloc_event_distance=1,...,heap_events_from_selected_pid=186,actual_ETW_event_adapter=1,synthetic_fixture_only=1`. Original identity transfer from *actual ETW payloads* is demonstrated under controlled conditions. Sixteen blocks deliberately outstanding at trace stop are not a leak.
2. **[Windows #45148410946 — SUCCESS](https://github.com/taku077/c545d-recorder/actions/runs/45148410946), job 137603331098**, **new observable** in a *single tiny ETW interval*: wait for native precleanup `finished.signal` after 64 alloc/16 realloc/48 explicit frees (16 held), then controller sends native `exit.signal`, native fixture frees the remaining 16 and exits, and only then ETW is stopped/decoded. Numeric results: `original_alloc=64,realloc=16,tracked_free=64,held_at_trace_stop=0,held_bytes=0,precleanup_held_milestone=1,postcleanup_free_verified=1,realloc_moved=16,realloc_inplace=0,raw_selected_free=80,realloc_after_provisional_free=16,max_provisional_free_to_realloc_event_distance=1,heap_events_from_selected_pid=254,actual_ETW_event_adapter=1`. A precleanup held-16 event-state was observed, followed by all 16 explicit frees and **zero selected fixture blocks remaining**, with logger loss-zero checked by controller. This proves the actual decoder can track full **alloc→realloc→held→free** lifetime; it does NOT prove a real GIO/APC/WinRT producer has quiesced.

The observed raw heap `Free` count (80) is **not** 80 application-level `HeapFree` calls: 16 are old-address events associated with realloc; 64 are the explicit fixture final frees. This is precisely why naïve count subtraction and treating `Out#>Alloc#` rows as invalid were wrong. There were 16 address relocations and no in-place reallocations in these two Windows native runs; in-place is tested by synthetic event fixture.

## Remaining actual-GIO questions — do not disguise as proven

- The C# adapter is deliberately gated to the known **360→720 byte synthetic fixture** and `GITHUB_ACTIONS/Windows/RUNNER_TEMP`. It **cannot** be invoked on the user's recorder or used to declare GIO owner attribution. Real-GIO memory sizes, stack owners and callbacks require separately validated allowlisting.
- The existing GIO ETW last4-of-16 trace begins after initial allocations. Original allocating address and stack for earlier objects may be absent. A free/realloc of such an orphan must be marked `capture_incomplete`, not assigned to GIO or guessed.
- A native process exiting after an explicit `exit.signal` is a **controlled producer-close boundary for this synthetic fixture only**. It does **not** prove that real GLib GIO registry watchers, Windows asynchronous APCs, WinRT callbacks and queued worker tasks are all shut down.
- Neither 16 held synthetic blocks nor actual GIO stack Out466 can be equated to the process PrivateUsage memory delta or 24/7 stability.
- PR #62 release remains `HOLD`; all 4 broad classification cases remain `EVIDENCE_GAP`; `install_approved=0,live_test_authorized=0,real_host_verified=0`.
