## What actually changed compared with old GIO ETW

Archived GIO ETW [#45015173260](https://github.com/taku077/c545d-recorder/actions/runs/45015173260) attached **after** running process started work, used **Circular** trace, and published only **top 25 module stack-frame occurrences**; no full alloc/free pair, buffer-loss proof or idle barrier in the final numeric evidence. It could not identify outstanding bytes and owner. Microsoft [Enabling Heap Data Capture](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/enabling-heap-data-capture) documents PID-specific tracing; [Using Actions to Analyze Process Heap Data](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/using-actions-to-analyze-process-heap-data) defines outstanding allocation and stacked size/count reports; [Avoiding Lost Buffers](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/avoiding-lost-buffers) requires verification of ETW lost counters.

New disposable test `tests/c545d_etw_owner_lifetime_calibration.c` deliberately executes **64 HeapAlloc(360)**, **48 HeapFree**, and **keeps 16** allocated until after trace stop. Its file signals enforce that all 64/48 operations happen after ETW is armed. The new `tests/Invoke-C545DEtwOwnerLifetimeCalibration.ps1` uses an existing-PID heap session (with **process waiting BEFORE the controlled workload**, no IFEO/GFlags/UST), `-FileMode Sequential` (not circular), `-stackwalk HeapAlloc+HeapRealloc`, and `-a heap -totals`. Local PDB and Microsoft public symbol configuration now permit `-a heap -stacks -size 360 361 -top 100`. On the small synthetic job, ETW logger statistics were parsed and **EventsLost / LogBuffersLost = 0**. The tiny synthetic ETL, PDB, raw addresses, stack report and status text remain in CI-private temporary storage and are deleted; no artifacts are uploaded.

### Classification progress — precise scope

The new calibration **fixes the prior sampling-design defect at the controlled workload boundary**, and verifies the Windows tool can write non-circular, zero-reported-loss heap data and symbolized size-filtered stack report. It **has not yet proven that the Xperf report itself reconstructs the exact 16 / 5,760 B**; do not claim that. The fixture intentionally keeps 16 allocations alive, which is *not a memory leak* if still within expected lifetime. Nothing is measured in GIO, WinRT, 256-cycle original Combo, or Tapo recording PC.

**Next distinct, falsifiable AI-only step:** implement a strict **local-only Xperf report schema/aggregate parser** and confirm its `Out number/Out size` counts are exactly the 16/5,760B known fixture at a checked barrier, with matching synthetic allocation stack and no lost events. If aggregation format makes exact size ambiguous, record the exact parse limitation and switch to a local ETW event reader rather than declaring "unknown". Only after this calibrator passes, transfer pre-workload barrier and bounded capture to the disposable GIO/WinRT probe with a real worker idle proof; stop trying unrelated memory micro-optimizations. Never upload raw ETL or identifiers.

Classification gate remains **OPEN** for `GIO16_OWNER_AND_COMMIT`, `GIO_COMBO256_LATE`, `GIO_ASYNC_QUIESCENCE`, `ACTUAL_TAPO_POSTPATCH`. Actual recorder safety/release gate **HOLD**. **No user action** and no implementation change approved for Windows10 recorder.

## NEW: verified synthetic source-owner reconciliation — Windows2022 (2026-11-23 JST)

The original calibration above reported the precise missing step: Xperf's **real output** had to reconstruct known synthetic outstanding blocks and their **source stack**, not just write non-empty reports. That step is now complete **for this synthetic fixture only**.

- [Windows Actions #45044677361 SUCCESS](https://github.com/taku077/c545d-recorder/actions/runs/45044677361), job 137276560024. `C545D_XPERF_OWNER_STACK_CALIBRATION_PASS,owner_stack_groups=1,synthetic_source_alloc=64,synthetic_source_outstanding=16,synthetic_source_requested_out_bytes=5760,synthetic_owner_symbol_matched=1,source_stack_report_unfiltered=1,source_specific_etw_calibrated=1,real_GIO_owner_proven=0,host_untouched=1,raw_stack_uploaded=0`.
- Source instrument `tests/c545d_etw_owner_lifetime_calibration.c` now uses a unique `__declspec(noinline) c545d_synthetic_owner_alloc_360` call frame; the Xperf unfiltered stack report **independently** counted 64 allocations and 16 outstanding blocks for that one source. The 48 expected frees are inferred from controlled source and counts (64−16); they are NOT separately established from the summary table as an individual list of 48 free event IDs. Those 16 are intentionally retained and **are not leaks**.
- New strict parser `tests/analyze_c545d_xperf_owner_stack_calibration.py` verifies the synthetic owner from the local **unfiltered** `-a heap -stacks -top 100` report; 7 negative fixtures and exact source numbers pass. Raw frames, PDB, ETL, paths and allocations are never uploaded or printed. Existing `tests/analyze_c545d_xperf_size360_totals_calibration.py` separately validates *size-filtered* whole-process Xperf `Out#=16`, Out KB approximately 5.6, and known sum by 360 B.
- **Important tool-specific limitation discovered and reproduced:** Xperf's combined `-stacks -size 360 361` report did not expose source frames (`synthetic_allocator_present=0`), whereas the unfiltered `-stacks` report included the unique synthetic function and recognizable symbol frames. Combining `-totals -size 360 361 -requireframes c545d_synthetic_owner_alloc_360` did not isolate it from unrelated process 360 B allocations. The method therefore uses the UNFILTERED stack report for owner attribution and a SEPARATE size-filtered total for block-size class. Do not reuse the ineffective combined filter in the actual GIO attribution gate.
- **Control contamination demonstrated:** process-wide size-filtered `Alloc#` varies ~78–85 across short identical runs rather than fixture 64, but its `Out#=16` is consistent. The `Alloc KB` field also does not simply equal `Alloc# × 360/1024` (e.g., 85 and 25.6 KB). Do not assume that aggregate's extra counts belong to the fixture or that its display is a precise byte-level allocation census. The unique source stack output resolves the *synthetic* 64/16 question; the process-wide Alloc KB/count discrepancy remains an explicit Xperf-report interpretation caveat, **not a newly proven leak**.
- The calibration's `-FileMode Sequential`, pre-workload armed PID, `EventsLost=0`, `LogBuffersLost=0` checks and local symbol cache remain required; commit [2756beb](https://github.com/taku077/c545d-recorder/commit/2756bebd2b75b311440ff4198005553c59285ff2) makes missing zero-loss or exact owner evidence fail closed, rather than printing unconditional success. Check latest CI for that final hardening commit before claiming it independently passed.
