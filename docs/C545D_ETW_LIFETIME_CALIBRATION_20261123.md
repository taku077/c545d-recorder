# C545D — pre-workload heap allocation lifetime calibration (2026-11-23 JST)

**CI only; Windows2022; source branch PR #62. No Tapo device, no GIO rebuild, no recorder process/settings/registry touched.**

## What actually changed compared with old GIO ETW

Archived GIO ETW [#45015173260](https://github.com/taku077/c545d-recorder/actions/runs/45015173260) attached **after** running process started work, used **Circular** trace, and published only **top 25 module stack-frame occurrences**; no full alloc/free pair, buffer-loss proof or idle barrier in the final numeric evidence. It could not identify outstanding bytes and owner. Microsoft [Enabling Heap Data Capture](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/enabling-heap-data-capture) documents PID-specific tracing; [Using Actions to Analyze Process Heap Data](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/using-actions-to-analyze-process-heap-data) defines outstanding allocation and stacked size/count reports; [Avoiding Lost Buffers](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/avoiding-lost-buffers) requires verification of ETW lost counters.

New disposable test `tests/c545d_etw_owner_lifetime_calibration.c` deliberately executes **64 HeapAlloc(360)**, **48 HeapFree**, and **keeps 16** allocated until after trace stop. Its file signals enforce that all 64/48 operations happen after ETW is armed. The new `tests/Invoke-C545DEtwOwnerLifetimeCalibration.ps1` uses an existing-PID heap session (with **process waiting BEFORE the controlled workload**, no IFEO/GFlags/UST), `-FileMode Sequential` (not circular), `-stackwalk HeapAlloc+HeapRealloc`, and `-a heap -totals`. Local PDB and Microsoft public symbol configuration now permit `-a heap -stacks -size 360 361 -top 100`. On the small synthetic job, ETW logger statistics were parsed and **EventsLost / LogBuffersLost = 0**. The tiny synthetic ETL, PDB, raw addresses, stack report and status text remain in CI-private temporary storage and are deleted; no artifacts are uploaded.

### Classification progress — precise scope

The new calibration **fixes the prior sampling-design defect at the controlled workload boundary**, and verifies the Windows tool can write non-circular, zero-reported-loss heap data and symbolized size-filtered stack report. It **has not yet proven that the Xperf report itself reconstructs the exact 16 / 5,760 B**; do not claim that. The fixture intentionally keeps 16 allocations alive, which is *not a memory leak* if still within expected lifetime. Nothing is measured in GIO, WinRT, 256-cycle original Combo, or Tapo recording PC.

**Next distinct, falsifiable AI-only step:** implement a strict **local-only Xperf report schema/aggregate parser** and confirm its `Out number/Out size` counts are exactly the 16/5,760B known fixture at a checked barrier, with matching synthetic allocation stack and no lost events. If aggregation format makes exact size ambiguous, record the exact parse limitation and switch to a local ETW event reader rather than declaring "unknown". Only after this calibrator passes, transfer pre-workload barrier and bounded capture to the disposable GIO/WinRT probe with a real worker idle proof; stop trying unrelated memory micro-optimizations. Never upload raw ETL or identifiers.

Classification gate remains **OPEN** for `GIO16_OWNER_AND_COMMIT`, `GIO_COMBO256_LATE`, `GIO_ASYNC_QUIESCENCE`, `ACTUAL_TAPO_POSTPATCH`. Actual recorder safety/release gate **HOLD**. **No user action** and no implementation change approved for Windows10 recorder.
